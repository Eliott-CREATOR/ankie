# Chantier 3 — Card atoms

Read `docs/spec.md` (§4 data model, §6 card design, §7 scheduling policy) and `docs/roadmap.md` §4
first. Branch: `c3-card-atoms`, cut from `main` at C2's merge (`33a5df4`). One checkpoint per step.

## Product objective

One word, several ways of knowing it. Today every word is a single recognition card: see the word
in its sentence, reveal the meaning. Knowing what a word means is not being able to use it. C3 turns
each word into **independently scheduled atoms** — recognition first, then production (produce the
word from its meaning) and usage (the words it goes with) — and only opens the harder atoms once
the easier one has actually stuck.

## User value

- Eliott practises *producing* a word, not just nodding at it — the real B2→C1 gap (spec §11).
- Harder cards appear only when earned, so a new word never arrives as a wall of three cards.
- He hears the word (Apple on-device voice, offline, zero bytes).
- Two easily-confused words are never introduced the same day.
- Common words come before rare ones in the new-card queue (after conversation words).

## Out of scope

Leeches, `ankie_get_leeches`, the optimizer, stats (C5) · offline/sync (C4) · short-term learning
steps (§3.1 open question, tied to C1) · any adaptive "how you remember best" logic (future ANKIE
Brain) · visual redesign (D-series: C3's UI is functional, D2 restyles it) · new MCP tools.

## Constraints carried forward

- Invoke `biome` and `tsc` directly. **Never swallow an error.**
- `cards.front`/`back` are materialized snapshots. Every write that changes sense content refreshes
  **every atom** of that sense in the same `db.batch()`.
- The recognition card's front/back must stay **byte-identical** to today's `materializeCard`
  (`0005` migration test). C3 adds shapes; it never changes the existing one.
- Card-atom logic is pure and lives in `packages/core` (spec §3); the Worker and PWA import it.
- The FSRS golden file does not change. `rateCard` does not change.

## The card model — the schema was designed for this

C3 needs **no destructive migration**. `cards` already has `atom_type`
(`recognition|cloze_production|collocation`), `state` including `locked`, `unlock_after_card`,
`unlock_min_stability`; `settings.production_gate_days = 21`; `lexemes.frequency_band`;
`senses.collocations` / `confusable_with`; `review_log.typed_answer`. `POST /api/review` already
refuses `locked` cards (409) and `GET /api/due` only serves `new|learning|review|relearning`.

| Atom | Eligible when | Starts | Unlocks when |
|---|---|---|---|
| `recognition` | always | `new` | — |
| `cloze_production` | `gloss_l1` present **and** a sentence contains the word | `locked` | recognition stability ≥ `production_gate_days` (21) |
| `collocation` | ≥ 1 collocation yields a single-partner pattern | `locked` | recognition stability ≥ 7 days (decision 1) |

**Budget:** register `archaic` or `literary` → recognition only (spec §6). Frequency does not cut
atoms (decision 3).

**Unlock mechanics:** each gated atom stores `unlock_after_card` = its recognition card id and
`unlock_min_stability` = its threshold. In `POST /api/review`, the same batch that updates the
recognition card runs `UPDATE cards SET state='new' WHERE unlock_after_card = ?card AND
state = 'locked' AND unlock_min_stability <= ?newStability`. One transaction, no job, no polling.
Unlocked stays unlocked.

### Shapes (the contract — `packages/core`)

Recognition — **unchanged**: front `{word, context_sentence}`, back
`{word, gloss_l1, definition_l2, context_sentence, examples}`.

Cloze production:
```ts
front: { sentence_blanked: string, hint_l1: string, first_letter: string }
back:  { word: string, answer: string, accepted: string[], sentence: string,
         gloss_l1: string, definition_l2: string | null }
```
- Sentence choice (decision 2): the first example containing the word, else `source_context` —
  recognition shows `source_context` on every review, so blanking it tests memory of a sentence,
  not production.
- Matching: case- and diacritic-insensitive via `normalizeLemma`, on whole tokens that **start with**
  the term (`conundrums` matches `conundrum`); `answer` is the surface form found; `accepted` =
  `[answer, term]` deduplicated. Blank = `____`. No match anywhere → no cloze atom.

Collocation:
```ts
front: { pattern: string, word: string }             // "____ a conundrum"
back:  { word: string, accepted: string[], collocations: string[] }
```
- Pattern: tokens of a collocation minus the term's token and function words
  (`a an the to of in on at for with by from into up`); exactly one content token left → it is the
  blank. First qualifying collocation is the pattern; `accepted` = the partner of every collocation
  producing the same pattern. None qualifies → no collocation atom.

Typed answers: `checkTypedAnswer(input, accepted)` → `"correct" | "almost" | "wrong" | "empty"`
("almost" = one edit away, answers ≥ 5 chars, after normalization). The check **informs, never
rates** — Eliott still picks Again/Hard/Good/Easy (decision 6).

## Database / API implications

**Migration `0006_card_atoms.sql` (additive only):**
- `CREATE UNIQUE INDEX idx_cards_sense_atom ON cards(sense_id, atom_type)` — one atom per type per
  sense; makes ingest/enrich/backfill idempotent. Fails loudly if duplicates exist (verify read-only
  on production before applying).
- `CREATE INDEX idx_cards_unlock ON cards(unlock_after_card)`.
- `ALTER TABLE settings ADD COLUMN timezone TEXT NOT NULL DEFAULT 'Asia/Singapore'` — spec §7 note
  assigns the local-day fix to C3, and "same day" rules below need a real day (decision 4).

**`GET /api/due`** — response stays `{cards, nextDueAt}`; each card gains **additive** fields:
`language_code`, `tts_voice_hint`, `frequency_band` (`DueCard = CardRow & {...}`). An old client
ignores them.

**`POST /api/review`** — optional `typedAnswer` (string ≤ 500) stored in `review_log.typed_answer`;
unlock update in the same batch; response gains `unlocked: number`.

**MCP** — no new tool, no contract break. `ankie_add_words` creates all eligible atoms in its
existing single batch. `ankie_enrich` refreshes every atom and creates newly eligible ones (a bare
word enriched with a gloss gains its cloze); its `card` field keeps returning the recognition card,
plus additive `atoms: [{atom_type, state, action}]`. `ankie_get_due_summary` gains additive `locked`.
Atoms are **never deleted** automatically; an atom that stops being eligible keeps its history and
content, reported as `action: "kept"`.

## Scheduling implications

FSRS still decides *when*, per atom. C3 changes only *what enters the day's queue*, as one pure
function `selectQueue` in `packages/core`:
1. **Local day** — daily limits and "today" use `settings.timezone` (`startOfLocalDay`).
2. **Sibling burying** (spec §7.3) — at most one card per sense per local day: skip a card if a
   sibling is already in the queue or was reviewed today.
3. **Confusables** (spec §7.2) — never introduce a new card whose lemma is confusable (either
   direction, normalized) with a card introduced today or already selected.
4. **New-card order** — conversation-sourced first (C2 rule kept), then unlocked non-recognition
   atoms, then frequency band (common → rare, unknown last), then insertion order.
5. New atoms consume `daily_new_limit` like new words.

**Frequency band:** a static JSON bundled with the Worker (spec §2), lemma → band `A` (top 2k) ·
`B` (2k–5k) · `C` (5k–10k) · `D` (10k–20k); absent → `null`. Set on ingest; backfilled. Source and
licence verified by Opus before bundling (decision 5).

## Migration strategy for existing words

Existing senses have one recognition card. `apps/worker/scripts/backfill-atoms.mjs` (Node, imports
`packages/core` like `seed.mjs`) reads an exported JSON of senses + recognition cards and writes a
reviewable `backfill-atoms.sql`: `INSERT OR IGNORE` atoms with deterministic ids (hash of
`sense_id:atom_type`) and `UPDATE lexemes SET frequency_band` where null. Gated atoms whose
recognition stability already clears the threshold are inserted `new`. Running it twice is a no-op.
Local first; **production application needs Eliott's approval** (it mutates production data, though
additively). No SQL copy of the new shapes — the TS generator is the only implementation.

## Backward compatibility

Recognition cards, their JSON, their schedule and review history are untouched. Old PWA builds keep
working (additive fields; locked atoms never served). `review_log` stays append-only. The C2 MCP
contract holds. Unknown `atom_type` in the PWA shows an explicit error for that card, never a crash.

## Acceptance criteria — THE GATE

**One word yields three correct atoms with the production card locked** (roadmap §4), shown on
production after approved migration + backfill + deploy:
1. A conversation word with gloss, examples and collocations → recognition `new`, cloze `locked`
   (21, → recognition), collocation `locked` (7, → recognition), all JSON correct.
2. Locally, raising that recognition card past each threshold unlocks exactly its atom; cloze and
   collocation render, accept a typed answer, and save `typed_answer`.
3. On Eliott's iPhone: the word is spoken; recognition cards look and behave as before.
4. Two confusable words added together are not both introduced on the same local day.
5. Biome · tsc · Vitest (golden unchanged) · web build · `wrangler deploy --dry-run` green; Terra
   review approves.

## Risks / product decisions (defaults applied — Eliott may override)

1. **Collocation is gated too** (recognition stability ≥ 7 days). The spec only gates cloze; a usage
   card before the meaning is known is noise. One constant.
2. **Cloze uses an example sentence first**, source sentence as fallback.
3. **Frequency orders, it does not cut.** Most of Eliott's words are rare-band ("prowess",
   "laconic"); cutting atoms by band would leave C3 almost empty. Only archaic/literary register
   limits a word to recognition.
4. **Daily reset moves to local midnight** (Asia/Singapore) instead of 08:00 SGT (UTC midnight).
5. **Frequency source** must be permissively licensed; a share-alike source gets an attribution file.
6. **Typed answers never auto-rate.** Ratings stay Eliott's; auto-suggested ratings are later work.
- Risk: heuristic sentence/collocation matching misses irregular forms (`went` for `go`) → the atom is
  simply not generated; Claude's enrichment can add a matching example later.
- Risk: queue changes are the most behaviour-visible part; `selectQueue` is pure and table-tested.
