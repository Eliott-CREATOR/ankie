## Step 2 — The review harness (before any app code)

This is the most important step in C0.

`.claude/CLAUDE.md` — the standards every future session inherits. It must state:
- No new abstraction without three concrete duplications
- No new dependency without a line here justifying it
- No file over ~300 lines without a reason
- Deterministic tools own formatting, linting, types and tests; the AI reviewer only reviews
  semantics
- Commits are conventional and scoped to one chantier

`.claude/hooks/` — a `PostToolUse` hook matching `Edit|Write` that runs `biome check --write` on the
touched file and then `tsc --noEmit` across the workspace. Wire it in `.claude/settings.json`.
Verify it actually fires; a hook that silently does nothing is worse than no hook.

`.claude/agents/code-reviewer.md` — a Claude Code subagent, NOT an API script. It runs in its own
context window, separate from the agent that wrote the code, which is the point: the reviewer must
not inherit the builder's reasoning. Its definition must:
- Take a chantier's base branch as input and read `git diff <base>..HEAD` plus the repo's key files
- Load `tools/review/rubric.md` and follow it exactly
- Output findings as a list, each classified `blocking` or `note`
- State plainly at the end whether any finding is `blocking`
- Use the strongest model available on this Claude Code subscription; if Claude Fable 5.1 is
  offered, use it

`tools/review/rubric.md` — kept as a standalone file, not inlined in the agent definition, so the
same rubric can drive a scripted API reviewer later without being rewritten. It contains these
rules verbatim:
  1. Never comment on anything Biome, tsc or Vitest already checks — formatting, naming a linter
     covers, coverage numbers. Semantics only: correctness under edge cases, security, data loss,
     genuine design problems.
  2. Classify every finding `blocking` or `note`. Only `blocking` forces a revision.
  3. "No findings" is a valid and good outcome. Do not invent work.
  4. Never propose a new abstraction unless there are three concrete duplications.
  5. Never propose changes that increase net line count without a correctness reason.
  6. Report only. Never edit code.

`.env.example` — currently only `REVIEW_MODEL`, documented as unused until a scripted API reviewer
exists. `.gitignore` already covers `.env`; verify it does before any commit.

**CHECKPOINT 2** — show me `rubric.md` and the subagent definition, and confirm the PostToolUse hook
fires on a test edit.
