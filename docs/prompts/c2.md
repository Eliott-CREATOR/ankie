## The gate this chantier exists to reach

**A word taught in a Claude conversation appears in Eliott's review queue with no action from him.**
No file, no export, no import, no "shall I build the deck now?". That is the feature the whole
project was started for.

## Out of scope

Card atoms beyond recognition, audio, the production gate (C3) · offline and sync (C4) · optimizer,
leeches, stats (C5). The `ankie_get_leeches` tool is C5 — do not build it here.

## Constraints carried forward

- Invoke `biome` and `tsc` directly, never through `pnpm` scripts.
- **Never swallow an error.** This project has now made that mistake twice: the C0 gate bug and
  `App.tsx` in C1. Every failure path either surfaces or throws.
- **`cards.front`/`back` are materialized snapshots.** Any write that changes sense content must
  refresh the card JSON too, or the database is right and the screen is stale. This already bit us
  once with `definition_l2`.
- Ids that cross the network are generated client-side and checked for duplicates before any write.
- The gate review runs in a separate Claude Code session on Fable, not a subagent.

## Step 1 — Auth: research and propose, do not build yet

Two callers hit one origin and they cannot use the same mechanism:

- **The PWA** — a browser, which can complete a Cloudflare Access login and hold a cookie.
- **claude.ai's MCP connector** — a machine. It cannot follow a login redirect any more than a
  `fetch()` can.

Research the *current* options for authenticating a remote MCP server to claude.ai — OAuth via
Cloudflare's MCP provider, a bearer secret in a Worker secret, Access service tokens — and report
what actually works today, with sources. Then propose one design covering both callers.

**CHECKPOINT 1** — your findings and a recommendation. Build nothing until I approve it. This is
the only step in the project so far where being wrong has a security consequence rather than a
correctness one.

## Step 2 — MCP server skeleton, proven end to end

- A remote MCP server on the existing Worker using `createMcpHandler` (Streamable HTTP)
- Exactly one tool: `ankie_ping`, returning a timestamp. Nothing that touches the database.
- The auth from Step 1, applied
- Registered as a custom connector on claude.ai

The point of a trivial tool is to prove the whole path — registration, transport, auth — before any
real logic is inside it.

**CHECKPOINT 2** — I call `ankie_ping` from a Claude conversation and see the response. Commit.

## Step 3 — `ankie_add_words`

```
ankie_add_words({ words: [{
  term, context_sentence,               // required
  language?, gloss_l1?, definition_l2?,
  examples?, collocations?, register?, domain?, confusable_with?
}]})
→ { added, duplicates_skipped, needs_enrichment: [term] }
```

- A bare `{term, context_sentence}` must be accepted and stored `enrichment_status='needs_enrichment'`
- Dedup on `lemma_norm` — a word already present adds no second card
- Write to `ingest_log`
- **Create the recognition card and materialise `front`/`back` in the same transaction as the sense**
- A `POST /api/ingest` endpoint accepting the same payload as CSV, for bulk imports

**CHECKPOINT 3** — words added from a conversation, dedup proven by adding the same word twice,
`ingest_log` populated. Commit.

## Step 4 — The read and repair tools

- `ankie_get_due_summary()` → counts, so Claude can say "you have 23 due"
- `ankie_get_pending_enrichment(limit)` → senses missing content
- `ankie_enrich(sense_id, fields)` → fill them, **refreshing `cards.back` in the same transaction**

That last parenthesis is the whole lesson from C1. If `enrich` writes only to `senses`, the
definitions problem returns and nothing will error.

**CHECKPOINT 4** — enrich a word that came in bare, and show the refreshed card JSON. Commit.
